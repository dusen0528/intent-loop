# Intent Loop

작업 요약과 별도로 현재 세션의 사용자 제약을 유지한다. 훅이 `pending`을 알리면 작업 도구를 실행하기 전에 검토 결과를 제출한다.

## 검토

- 현재 제약과 미검토 사용자 메시지를 대조한다. 여러 메시지가 밀려 있으면 모두 검토한다.
- 지속되는 행동 제한, 정보 취급, 작업 절차, 선호, 출력 조건을 기록한다. 작업 진행 로그와 모델 가정은 제약으로 등록하지 않는다.
- `가능하면`, `이번 작업에서`, `승인 전` 같은 강도·범위·조건을 보존한다.
- 사용자 변경은 `replace`, 명시적 철회는 `remove`, 새 제약은 `add`로 제출한다. 기존 항목의 ID를 유지한다.
- 각 변경의 `source_quote`는 미검토 메시지의 실제 원문 구절이다. 출처나 승인 사실을 만들어내지 않는다.
- 변경이 없다고 판단했을 때만 `[]`를 제출한다. 잠금을 풀기 위한 형식적 제출은 하지 않는다.

## 제출

훅이 출력한 Python 실행 경로, 스크립트 경로, 상태 경로, `review_id`를 그대로 사용한다. 마지막 JSON 인자만 검토 결과로 바꾼다.

```json
[{"op":"add","id":"c1","text":"원본 파일을 삭제하지 않는다.","source_quote":"원본은 삭제하지 마"}]
```

`replace`는 같은 필드, `remove`는 `op`, `id`, `source_quote`만 필요하다. JSON 전체를 하나의 셸 인자로 안전하게 인용한다. 훅의 예제처럼 단일 인용을 사용하고 내부 작은따옴표는 셸의 `'"'"'` 연결로 표현한다. 명령 뒤에 다른 작업, 리다이렉션, 파이프를 붙이지 않는다.

제출이 실패하면 오류를 수정한다. 오래된 ID이면 최신 훅 안내를 사용한다. 상태 파일을 직접 편집해 검토를 완료 처리하지 않는다.

## 재개와 불확실성

- 압축·재개 후 복원된 제약을 계속 적용한다. `reviewed`이면 재제출하지 않는다.
- 결정이 불명확하고 다음 행동을 바꾼다면 질문한다. 매번 사용자에게 전체 목록을 재승인받지는 않는다.
- 사용자 지시·상위 지침·호스트 권한과 충돌할 경우 복원된 메모가 우선하지 않는다. 승인 필요 제약의 기록은 실제 승인이 아니다.
- 별개 작업은 새 세션을 사용한다. 이전 세션의 제약 파일을 복사해 자동 승계하지 않는다.
- 훅이 없으면 이 스킬만으로 실행 차단이 생기지 않는다. 설치·활성화 또는 의미 정확도가 검증됐다고 주장하지 않는다.
